# 任务文档 · 钟杭延 · 第三部分：dsh 插件

> 分支 `feat/dsh-plugin`（或独立仓库）｜提交前缀 `feat(dsh):`
> 一句话：给 deepseek harness 设计并实现一个插件，解决现有市场插件没覆盖的问题，能装上、能演示、能写清文档。

## 0. 上下文

- dsh 是**微内核 + 插件**的 Agent 平台，"一切皆插件"。本机已装 DeepSeek Harness，可以直接对着自己的环境开发。
- 任务书里给了十个市场插件作参考（`dsh-market`、`dsh-find-plugin`、`DSH-better-sidebar`、`dsh-web-ui`、`ModLens`、`dsh-vision-toolkit`、`dsh-genui`、`dsh-TUI`、`dsh-mnemon`、`dsh-browser`）；更多在 GitHub 的 `dsh-plugin` 主题下。
- **与第一、第二部分完全解耦**：不依赖 CLI 任何代码，D0 就能开工；`docs/metrics/` 的 CLI 指标里也不算你。

## 1. 交付清单

```text
dsh-plugin/
├── README.md          # 一句话介绍、安装、使用、限制
├── package.json       # name / contributes / dsh 版本要求
├── src/               # 插件实现
├── test/              # 最小测试
├── demo/              # 可复现的演示会话（命令与预期输出）
└── DESIGN.md          # 设计文档
doc/parts/dsh.md       # 提案 + 设计摘要（会合并进 doc/README）
```

建议放**独立仓库**（`dsh-<name>`）并在 lab1 的 `doc/parts/dsh.md` 里放链接：这样不会污染 CLI 的指标统计，也方便以后发布。

## 2. 任务

| # | 任务 | 内容 | 完成标准 |
|---|---|---|---|
| D1 | 选题 | 翻市场插件与源码，找空白。明确三件事：增强什么能力、谁会用、现有插件为什么没解决 | 一页提案；能说出至少两个"不重复造轮子"的理由 |
| D2 | 设计 | 插件形态（tool / command / UI / 记忆层）、`contributes` 声明、与 dsh 微内核的边界、失败与权限策略、状态放哪 | `DESIGN.md` 里有接口草案，别人照着能实现 |
| D3 | 实现 | 插件主体、参数校验、错误处理、日志；不依赖本机未提交的临时改动 | 干净环境能装、能跑 |
| D4 | 测试 | 装进本机 dsh，跑通 demo；覆盖正常路径 + 参数错误 + 依赖缺失 | 至少 1 段可复现会话，输出符合设计 |
| D5 | 文档 | README 写安装/使用/限制；可选发布到插件市场 | 按 README 一次装成功；未发布就写明原因 |

**选题时的判断标准**（按优先级）：

1. 是不是"我现在每天用 dsh 都会缺"的能力？（真实痛点评分最高）
2. 能不能先做出一版能用的最小实现？（先窄后深，别做平台）
3. 有没有清晰的失败边界？（外部命令、文件、网络都容易出事）

避免的方向：再做一个插件市场、再做一个侧边栏、再做一个视觉模型转接——这几个已经很拥挤，除非你有明显不同的切入点。

## 3. 自验清单

- [ ] 干净环境（或至少清空本地配置）按 README 步骤安装成功
- [ ] 启动 dsh，插件出现在预期的位置（命令 / 工具 / 面板）
- [ ] 跑 demo 会话：输入、输出、副作用（改文件/调外部命令）都符合 `DESIGN.md`
- [ ] 参数错误的调用：报错清晰、不崩溃、不留下半截状态
- [ ] 依赖缺失（比如需要的命令不存在）：有明确提示
- [ ] 关掉插件后 dsh 正常启动，说明卸载干净
- [ ] README 里的每条命令都亲手跑过一遍

## 4. 接口交接

- **不依赖任何人**，也不需要给别人提供东西。
- 唯一要配合的：`doc/parts/dsh.md` 交给张子超合并；如果发布到市场，把仓库链接和安装命令给他。

## 5. 容易踩的坑

1. **dsh 还在开发者预览期，接口会变**：先把版本要求写进 `package.json`，README 里注明"验证于 x.y.z"。
2. **权限最小化**：读文件、跑命令、访问网络都要在设计文档里说明理由；不要顺手读用户主目录。
3. **别把 demo 做成"只有我机器能跑"**：demo 里的路径、环境变量都写成相对路径或占位符。
4. **发布前审一遍自己的代码**：任务书明确提醒"安装第三方插件前应审查源码"，你自己发的插件更该干净。
5. **时间盒**：选题与设计放在最前面两三天内收口，迟迟定不下来就砍成"小而完整"，不要拖到最后。
6. **不要依赖 CLI 的代码**：这一块是为了和第一、第二部分并行才交给你一个人的，跨过去会互相拖。
